# Named Summaries and recipient access (version 2)

This extension supersedes the singleton configuration, publication, and cursor rules in NIP-BR for configurations and reports whose content has `v: 2`. Version-one configurations and historical reports remain readable. This is relay-enforced access control over plaintext stored by the relay, not end-to-end encryption or protection from relay operators.

## Identity and audience

A Summary is keyed by community, owner public key, and a canonical UUID. The migrated singleton uses `default` and keeps its `d=summary` address; new definitions use `d=summary:<uuid>`. Owner-signed kind 30623 definitions contain name, reporter, audience, explicitly selected channels/DMs, schedule, timezone, pause/archive flags and read-delegation consent. Only the owner and assigned reporter receive the configuration. Preselecting new conversations in the editor does not silently grant them access.

Audiences are `only_me`, `community`, or `selected` with human public keys. The owner is always included. Human discovery joins the community's relay membership roster with active user records, excluding agent ownership/type and bot membership flags; offline people remain eligible. Missing profiles are not assumed human. Open relays advertise an incomplete directory and cannot select the community audience. The picker uses the same searchable dialog as agent delegation with a separate authoritative people data source.

The relay snapshots recipients for each run. Newly added recipients cannot read older reports. Live audience removal, community departure, and private-source membership removal block subsequent reads through history, direct IDs, counts and live fanout. Recipients must already be eligible to read every private source; community reports accept only community-readable sources. The reporter gets readback of its own reports while it remains the assigned reporter. View permission does not grant edit/run control or source membership. Already downloaded copies cannot be recalled. Named reports do not generate agent push wakes or notifications containing private metadata.

## Scheduling and execution

Desktop stores either manual-only, the existing Workflow cron/interval controls, or explicit daily `dailyTimes` in HH:MM form. Daily times are grouped by minute into separate cron workflows; 09:15 and 17:45 never become a cross product of hours and minutes. All workflows carry a literal `run_summary` action and use the saved IANA timezone. Pausing stops automatic runs while retaining manual execution; archiving prevents new execution and retains reports. Name, schedule and timezone edits preserve active work. Changing the reporter, audience, source set, read consent or archived state invalidates previously claimed grants. Existing runs never silently adopt a new audience or source set.

The Workflow engine retains its existing missed-tick behavior: cron checks a 60-second window and does not replay every missed occurrence after a long outage. Interval anchors are durable. Source cursors remain unchanged during outages, so the next successful run reads the accumulated delta. A first run reads the preceding 24 hours. After a successful run, late relay arrivals with older event timestamps are included as unread activity; a published read receipt prevents them from being repeated. An empty delta can publish a factual no-new-activity report with no cursor changes. Cards show the next planned cron trigger in the saved timezone. Interval previews require a durable scheduled-fire anchor; manual runs are never used as interval anchors.

Manual and scheduled claims share a writer-locked execution slot per Summary. A new claim is immediately `running`; concurrent callers receive the same run instead of dispatching again. Runs freeze the definition, audience and upper time boundary, with a 30-minute lease. Reporter progress can record `needs_approval`, return to `running`, or mark `failed`. The owner can cancel to `failed`. Terminal receipts cannot be reopened. On a new claim, expired or superseded runs become failed without moving cursors. The database also reserves a queued state for dispatch integration; it is not currently emitted. Manual and scheduled dispatch are serialized across relay processes. Relay-managed claims record that delivery belongs to the relay; a durable relay-authored request is bound to the run. Retrying an interrupted dispatch reuses the run and looks for that request before sending. Externally started claims are not silently redispatched. Delivery uncertainty appears in run history with a cancel-and-retry recovery action; publication and reading progress remain protected by the original run identity. Progress never extends a lease.

## Agent operations

Use `buzz briefs run status --owner <key> --summary <id> --run <uuid>` to retrieve a private receipt, definition and independent cursors. Read only selected sources using `buzz briefs read --owner <key> --summary <id> --run <uuid> --channel <id>`; the reporter does not need membership in a delegated DM. This grants no ordinary channel subscription or write capability. Read authorization is checked before and after retrieval against writer state. Only rows actually returned by this operation become observed-read receipts. Follow `next.until` and `next.before_id` while `has_more` is true. Every source, including an empty conversation, needs a read receipt; observing only the newest watermark is insufficient. Publication rejects any eligible unread gap.

The agent writes composition JSON containing `title`, `markdown`, `status` (object), `sources` (channel IDs), and `watermarks` (objects with `channel_id`, `event_id`, `created_at`). It then calls `buzz briefs run publish --owner <key> --summary <id> --run <uuid> --input <file-or-dash>`. The host constructs the authority-bearing envelope; the agent cannot choose another reporter, revision, audience or run boundary. The CLI checks the durable publication receipt even after a missing submission acknowledgement. A generic conversation-report receipt is not Summary success.

Use `buzz briefs run progress` with the same identity flags, `--state running|needs_approval|failed` and an optional `--message`. A needs-approval run cannot read or publish until resumed. Owners may only use progress to cancel; recipients cannot enumerate run status/history/cursors.

## Atomic publication and migration

Kind 40030 carries explicit owner, summary, run and config identity tags plus the frozen audience and executing reporter. The relay rechecks execution authority, agent ownership, audience and source access in the publication transaction. Every proposed watermark must match a server-observed event in this run and source. Actual report storage, recipient indexes, cursor advancement and the published run receipt commit together. A failed transaction leaves all four unchanged. Identical retries do not advance cursors twice; a different second report for the same run is rejected.

Cursors are scoped to community/owner/Summary/source, independently of reporter identity. Migrating the singleton copies its selected-source legacy watermarks once, preserving their original watermark-event provenance, and leaves historical reports intact. Separate Summaries sharing one agent and source have independent boundaries. The additive migration is `0051_summary_runs.sql`; older relay binaries cannot enforce version-two access semantics, so clients require the version-two capability response before saving.

## Verification

Database acceptance tests live in `crates/buzz-db/src/store/summary_tests.rs`; relay-handler tests live in `crates/buzz-relay/src/api/bridge/summary_tests.rs`. These require explicitly isolated Postgres (and Redis for the relay fixture). They cover independent cursors, overlapping claims, atomic/idempotent publication, unobserved-cursor rejection, source revocation, roster classification, migration, expiry, progress and restart receipts. The modules end in `postgres_tests` so the isolated PostgreSQL CI lane discovers them automatically. Handler tests use three humans, an assigned reporter and an unrelated agent for direct-ID/config privacy, frozen community audiences, counts, fanout and delegated reads. The browser test `desktop/tests/e2e/summary-setup.spec.ts` exercises the guided editor, canonical agent picker, people picker, duplicate definitions, manual run and exact multiple daily times. Browser mocks are UI evidence only; they do not prove live publication.

## Report archive and deletion

The report library uses authenticated `reports_list` control queries with server-side literal text, owner/Summary, reporter and publication-date filters. Keyset pagination orders by publication timestamp and event ID; pages contain at most 50 reports. Every returned report is reauthorized against current audience/source membership. Public cursors only reference authorized results. A bounded scan of withdrawn candidates can ask the reader to narrow filters rather than return an inaccessible cursor or unbounded history. General workspace search continues to exclude private Summary bodies.

Migration `0052_summary_report_archive.sql` adds per-community, per-reader archive state and a partial history index. `reports_archive` and `reports_restore` accept explicit selections of at most 50 report IDs. Archiving changes only that reader's organization, retains the report, and has no effect on schedules or another recipient's archive. The Summary archive also presents archived definitions separately; restoring a definition restores its prior scheduling configuration.

`reports_delete` is owner-only and the Desktop requires confirmation for both individual and bulk deletion. The relay validates the complete selection before applying a transaction. Deletion uses the existing event deletion marker: reports disappear from relay reads, but their database payload and backups are not physically purged. Run receipts, report identity and source cursors remain, and replaying a previously published report does not restore it. Previously downloaded copies cannot be recalled. Other open clients refresh their Summary views on the normal polling interval.

Archive storage is additive metadata, not an alternative location for report content. The authoritative report remains in relay PostgreSQL. Client page sizes bound rendering/network payload per query; text filtering may still scan matching relay records and is not a claim of constant-time search at arbitrary scale. Retention or physical purging is a separate operator policy, not silently enabled by archiving or deletion.


## Reliable save and compatibility

Migration `0053_summary_read_coverage.sql` adds complete-source receipts, schedule ownership, regeneration metadata and an index for consumed reads. The signed definition is now the schedule authority: its derived workflow rows are created or disabled in the **same database transaction**. The owner-signed `previous` tag checks the editor revision. New definitions use an empty predecessor; stale edits fail visibly. Old linked workflow definitions are retired during conversion. Derived jobs are managed through Summary setup, not edited as independent Workflow documents. Jobs carry the exact configuration generation and cannot execute after a newer manual-only, paused or archived save.

The new Desktop requires `summary_protocol: 2`, `summary_report_archive: 1`, and `summary_hardening: 1`. Unsupported relays show an update requirement; a network failure offers retry rather than being diagnosed as an unsupported relay. Existing stored reports are not deleted by this gate. Deploy the additive relay migration before the new Desktop. Older clients may continue to read their supported signed report formats, but are not the supported editor for relay-managed schedules. No older binary should be used to write version-two Summary data after a downgrade without a reviewed migration plan.

## Reading, sharing and regenerating reports

`reports_list` with `metadata_only: true` returns bounded identity/coverage metadata; `reports_get` loads an individually authorized report and its metadata. No list preview authorizes a later detail read. Definition history is paginated independently, and collection counts cover the complete owned history rather than a shared first page. Shared report metadata identifies the Summary, owner and agent. Filters and page positions are retained in memory during the app session and scoped to the reader and relay; bulk selections do not carry across archive modes.

A `buzz://summary?id=<event>&relay=<websocket-url>` link opens the exact report through the same live authorization. It never joins an unknown relay or grants access. The reader also supports copying and Markdown export. Exported copies are outside relay revocation.

An explicit owner-confirmed regeneration dispatch supplies `source_report`. The relay checks the original report, owner, Summary identity and current read permission, then freezes its historical period on a new run. Current saved sources, reporter and recipients apply. Normal cursors are not used to truncate that interval, and publication does not update them. The original report remains unchanged. Deleting a report alone never rewinds progress; ordinary Run continues unread work. Already active runs are surfaced rather than replaced by a regeneration click.

## Storage and operator retention

Archiving has no automatic retention or physical-purge effect. Readers can archive/restore their own view; only the Summary owner can mark a report deleted for everyone. Payloads, run receipts, observed reads, deletion markers and backups may remain. Operators must document backup expiry and any physical-purge process separately. A purge must preserve replay/deletion protections and consumed-read evidence, or replace them with an equivalent durable boundary before removal. Do not prune read receipts simply because the report was archived or deleted. No automatic purge is enabled by this feature.

A local isolated fixture with 1,000 reports, three human identities, two agents and 15,600-byte synthetic report bodies measured a 50-report metadata page at 24,226 bytes versus 845,575 bytes for full events. One observed local request took 297 ms for metadata and 265 ms for full events. This demonstrates reduced transfer size, not a universal latency improvement or production capacity guarantee. Per-report live authorization still contributes database work; large or highly revoked histories and arbitrary text searches require deployment-specific measurement. Collection polling is suspended while editing or browsing the report library.

Five-field custom cron schedules use ordinary Unix weekdays (0 or 7 = Sunday, 1 = Monday); the relay translates these to day names before execution. Six- and seven-field expressions retain the workflow engine's native convention. The next-run display uses the same translation. Search covers report text plus Summary, owner and agent names across the full accessible history; dropdown suggestions grow from accessible pages and owned setups.

The CLI obtains `coverage_since` from the relay's observed reads and per-source boundaries, so the displayed period includes delayed activity rather than deriving its start only from the newest watermarks. Publications must name every configured conversation and include all observed message timestamps in their period. Empty conversations still require an explicit read receipt before complete coverage can be claimed.
